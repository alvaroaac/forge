HANDOFF: Project Forge — Engineering Command Center

# Context
We have completed an initial brainstorming and planning session for a project codenamed Forge. The goal is to build a personal desktop engineering command center that connects Linear, Claude Code, and Codex CLI into a unified workflow for spec generation, issue management, and agent orchestration.

## About the developer

- Senior Software Engineer, 8 years experience, 3 in startup leadership
- Stack: React, Node, TypeScript, GraphQL, Prisma, Java, React Native
- Works on a single monorepo
- Already has: a Claude Code–based orchestrator core (mix of skills and scripts, plugin-style), Linear integration skills/scripts, and an established thoughts/ folder convention for AI thinking (repo-scoped)
- Uses CLAUDE.md at repo root as the primary context file for agents
- Has an agentic development methodology called Ralph Mode: stateless agent loops with filesystem-persisted progress, skill-based orchestrator with separate performer and QA reviewer agents, tool-agnostic across Cursor and Claude Code


# What Forge is
A desktop app (Electron + React) that:

- Pulls assigned Linear issues for a specific sub-team (already modeled in Linear, filter config not needed for MVP)
- Generates structured spec reports for issues using repo context + Claude API
- Lets the user act on a spec by spawning Claude Code or Codex CLI agents directly from the UI
- Keeps the Linear board in sync via a background service
- Uses thoughts/ as the shared memory/handshake layer between the user and all agents


## Architecture

```text
Electron Shell
├── Renderer (React UI)
│   ├── Dashboard (today's issues, agent status)
│   ├── Issue Detail + Spec Report view
│   └── Agent Launcher (Claude Code / Codex)
├── Main Process (Node)
│   ├── Linear Sync Service (background polling)
│   ├── Agent Runner (spawns CLI processes)
│   ├── Spec Generator (reads CLAUDE.md + thoughts/ + issue)
│   └── Auth Checker (validates CLI login state)
└── Local Storage (SQLite or flat JSON)
    ├── Issue cache + TODO list
    └── Spec report history
```

## Spec Report format (MVP)
Generated by reading CLAUDE.md + thoughts/ + Linear issue content, then calling Claude API. Output is a structured markdown doc containing:

- Task summary
- Context from codebase conventions
- Suggested approach / high-level steps
- Open questions

### Agent spawning

- Agents are spawned as real CLI processes (node-pty + xterm.js terminal pane inside Electron)
- Two options per spec: Implement with Claude Code or Implement with Codex
- Auth: on startup, verify both CLIs are logged in — if not, prompt the user to log in manually, no programmatic auth handling
Spec must be marked as approved before an agent can be spawned


## `thoughts/` convention

- Already an established standard in the developer's workflow
- Repo-scoped for this project
- Every spawned agent reads thoughts/ on init for context
- We need to standardize this and shape this folder for this project
- Phase 3 will formalize this as a golden template scaffolded on first run


## Phased plan
### Phase 1 — MVP: "See your board, generate a spec"

- Electron + React shell
- Linear polling: fetch assigned issues for sub-team, render as TODO list
- Auth checker on startup
- Issue detail view
- Spec Generator: reads CLAUDE.md + thoughts/ + issue → calls Claude API → renders structured markdown spec in UI
- Spec is copyable
- Milestone: open app → see issues → click issue → read spec in 30 seconds

### Phase 2 — "Act on it"

- Agent Launcher: spawn Claude Code or Codex CLI from spec view (node-pty + xterm.js)
- Review flow: feedback field on spec → posts as Linear comment
- Spec approval gate before agent spawn

### Phase 3 — "Background sync + thoughts/ discipline"

- Linear Sync Service as proper background daemon
- Detects issue status changes, updates TODO list
- Spec → thoughts/tasks/[issue-id]/initial-spec.md writer (actual path TBD)
- Scaffold thoughts/ golden template on first run -> There needs to be a minimal structure we need to brainstorm

### Phase 4 — "Orchestration"

- Integrate existing orchestrator core skill
    - need to verify, potentially update/adapt
- Spawn orchestrator for bigger issues: breaks into sub-tasks, executes sequentially, reports back
- Progress view: running agents, status, output tailing

### Phase 5 — "Productization"

- Config UI: repo path, Linear team/filter, agent preferences
- Onboarding wizard: connect Linear, verify CLI auth, set repo
Theming, polish, packaging (electron-builder, auto-update)
- Plugin system: skills map to installable extensions
- Target: sellable as B2B SaaS or self-hosted personal tool


# Key architectural decisions

- Local-first: no backend, Linear is source of truth, until Phase 5+
- thoughts/ is the agent handshake protocol — every agent reads it on spawn
- Structured doc templates defined from day 1 — spec format, thoughts format must not drift
- Everything sellable-aware from the start: config-driven, no hardcoded paths or assumptions
